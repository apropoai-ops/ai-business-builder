## Project bindings

These are this repository's answers to the rules the managed block states in the
abstract. They are not optional context — a component that follows the managed
block but ignores these will not match the codebase.

- **Semantic tokens, never raw hex.** Storefront colour comes from the
  business's own brand, resolved through `lib/storefront-brand.ts`
  (`brandOnDark`, `inkOn`, `brandInk`) — those helpers are what guarantee the
  contrast ratios the managed block requires. A literal `#ff2f2f` in a
  storefront component is a bug: the reference brand's red is one tenant's
  value, not a system token.
- **Design tiers.** Every site renders the `professional` tier
  (`lib/design-tier.ts`). Tier CSS paints `[data-el="hero"] h1` with its own
  gradient, so a hero that sets its own headline colour must neutralise that
  rule explicitly (see the `[data-tier="professional"]` blocks in
  `components/public/heroes/*.tsx`).
- **Hero styles.** The registry is `lib/hero-style.ts`; the dispatcher is
  `components/public/heroes/store-hero.tsx`; the owner-facing swatch is
  `components/business/hero-style-picker.tsx`; the AI picker's prompt is in
  `lib/actions/design.ts`. A new style must land in all four plus
  `tests/hero-style.test.ts`.
- **RTL is the default.** Use logical properties (`ms-`/`me-`, `ps-`/`pe-`,
  `text-start`/`text-end`, `inset-inline-*`). Physical `left`/`right` in a
  content component is a bug; in an absolutely-positioned decorative layer it
  is acceptable.
- **Hebrew first when choosing type.** A Latin-only display face silently falls
  back to a system font on Hebrew copy. Verify Hebrew coverage before adopting
  a family, and pair it with a Latin face rather than the other way round.
- **Motion must degrade.** Every animation needs a
  `@media (prefers-reduced-motion: reduce)` branch, and pointer-driven effects
  need a `(hover: none)` branch.

### Additional rules (from the authoring brief, kept out of the managed block)

- Interactive components **must** document keyboard, pointer, **and** touch
  behavior — not keyboard alone.
- Component guidance **must** state responsive and edge-case handling.
- Accessibility acceptance criteria **must** be testable in implementation.
- Guidance **should** include the reference page's component density so rules
  are sized to real usage: buttons (191), links (138), inputs (37), lists (27),
  navigation (5), tables (1). A rule that is cheap for one button is not
  automatically cheap for 191.
- Teams **should** prefer system consistency over local visual exceptions.
- The authoring workflow **must** end with a QA checklist, and **should**
  include anti-patterns and migration notes before it.

# חנות בגדים לגברים

## Mission
Deliver implementation-ready design-system guidance for חנות בגדים לגברים that can be applied consistently across e-commerce storefront interfaces.

## Brand
- Product/brand: חנות בגדים לגברים
- URL: https://www.maniajeans.co.il/
- Audience: online shoppers and consumers
- Product surface: e-commerce storefront

## Style Foundations
- Visual style: structured, accessible, implementation-first
- Main font style: `font.family.primary=Helvetica`, `font.family.stack=Helvetica, Almoni, Arial, sans-serif`, `font.size.base=16px`, `font.weight.base=400`, `font.lineHeight.base=22.4px`
- Typography scale: `font.size.xs=0px`, `font.size.sm=12.8px`, `font.size.md=16px`, `font.size.lg=19.2px`, `font.size.xl=24px`
- Color palette: `color.text.primary=#161616`, `color.text.secondary=#ffffff`, `color.text.tertiary=#ff2f2f`, `color.text.inverse=#d2242a`, `color.surface.base=#000000`
- Spacing scale: `space.1=6.4px`, `space.2=8px`, `space.3=12px`, `space.4=16px`, `space.5=32px`, `space.6=108px`, `space.7=128px`
- Radius/shadow/motion tokens: `radius.xs=4px`, `radius.sm=32px`, `radius.md=38.4px` | `shadow.1=rgba(0, 0, 0, 0.1) 0px 0px 8px 0px` | `motion.duration.instant=200ms`, `motion.duration.fast=250ms`, `motion.duration.normal=600ms`

## Accessibility
- Target: WCAG 2.2 AA
- Keyboard-first interactions required.
- Focus-visible rules required.
- Contrast constraints required.

## Writing Tone
concise, confident, implementation-focused

## Rules: Do
- Use semantic tokens, not raw hex values in component guidance.
- Every component must define required states: default, hover, focus-visible, active, disabled, loading, error.
- Responsive behavior and edge-case handling should be specified for every component family.
- Accessibility acceptance criteria must be testable in implementation.

## Rules: Don't
- Do not allow low-contrast text or hidden focus indicators.
- Do not introduce one-off spacing or typography exceptions.
- Do not use ambiguous labels or non-descriptive actions.

## Guideline Authoring Workflow
1. Restate design intent in one sentence.
2. Define foundations and tokens.
3. Define component anatomy, variants, and interactions.
4. Add accessibility acceptance criteria.
5. Add anti-patterns and migration notes.
6. End with QA checklist.

## Required Output Structure
- Context and goals
- Design tokens and foundations
- Component-level rules (anatomy, variants, states, responsive behavior)
- Accessibility requirements and testable acceptance criteria
- Content and tone standards with examples
- Anti-patterns and prohibited implementations
- QA checklist

## Component Rule Expectations
- Include keyboard, pointer, and touch behavior.
- Include spacing and typography token requirements.
- Include long-content, overflow, and empty-state handling.

## Quality Gates
- Every non-negotiable rule must use "must".
- Every recommendation should use "should".
- Every accessibility rule must be testable in implementation.
- Prefer system consistency over local visual exceptions.
